# IT-AMS v2: Production Readiness (Hardware Asset Module)

Scope: hardware assets, accessories, users, procurement, stock ledger, maintenance and New Joinees.
Software, heartbeat and endpoint-agent modules were not changed in this pass.
Stack unchanged: Node.js + Express + EJS + PostgreSQL. Database data was preserved; `.env` was not modified.
Backup taken before this pass: `storage/backups/before-production-readiness.sql`.

## 1. Issues fixed

| # | Area | Issue | Fix |
|---|---|---|---|
| 1 | Pagination | Stock Movements showed only the latest 250 rows (no paging) | SQL `LIMIT/OFFSET` paging over all 39k+ movements; ids paged first, then joined |
| 2 | Pagination | Maintenance capped at 500 rows | SQL paging (25/page) with filters kept in page links |
| 3 | Pagination | Procurement detail listed every linked asset (up to 1,700+) | SQL paging (50/page) |
| 4 | Pagination | `GET /api/assets` returned the first 1,000 full rows, ignoring location scope | Paged (`?page`, `?per_page` ≤ 200), location-scoped, `X-Total-Count` header; still a JSON array |
| 5 | Pickers | Maintenance and inventory still preloaded 1,000 users/assets they no longer displayed | Preloads removed; every picker queries `/api/pick/*` (max 20 results, permission-checked) |
| 6 | Pickers | Maintenance picker had to keep the "no lost/retired/disposed" rule | New `/api/pick/maintainable-assets` source |
| 7 | N+1 | Stock ledger ran 1–2 queries per row (up to ~500 per page) and per row on CSV export | Single query with LEFT JOINs |
| 8 | N+1 | Sidebar ran ~2 permission queries per nav item for non-admin users | Permissions loaded once per request |
| 9 | Full scans | Catalog overview loaded whole tables just to count them | `COUNT(*)` subqueries |
| 10 | Indexes | Every search/list query was a sequential scan | `database/performance_indexes.sql`: pg_trgm GIN indexes on asset tag/serial/name/model, employee name/email/CTID, accessories, models, PO numbers; b-tree indexes on status, location, model, category, assignee, assignments, warranty expiry, and list sort keys. Searches went from 8–20 ms to under 1 ms |
| 11 | Data leak | QR codes (asset labels, asset page, **2FA setup secret**) were generated by api.qrserver.com | Local generation with the `qrcode` package (PNG data URIs) |
| 12 | Data leak | Google Fonts called on every page (user IP, app origin) | Inter/Outfit self-hosted via `@fontsource`, served from `/fonts/*` |
| 13 | Hardening | CSP still allowed unpkg, jsdelivr, tailwind CDN, rawgit, Google Fonts, qrserver | CSP is now `'self'` only (+ `data:` images) |
| 14 | New Joinees | Every page view opened a write transaction and locked all pending/draft joinee rows | Read-only `EXISTS` check first; generation only runs when needed, uses `FOR UPDATE SKIP LOCKED`, and runs once per process at a time. Stale drafts (laptop taken since) are re-recommended. Workflow unchanged: joinee → recommendation → SPOC review → allocate |
| 15 | New Joinees | No way to pre-generate recommendations | `node bin/hams-cli.js joinees:recommend` (for cron or after a bulk joinee import) |

Verified: 10/10 tests pass; 77/77 EJS templates compile; 83 pages and detail views return no 4xx/5xx and none is over 200 KB;
pickers return ≤ 20 rows in 13–40 ms; no third-party requests from any page tested.
The CSV/Excel export is only read by `tools/import-asset-data.js` (CLI). No page reads files; all data comes from PostgreSQL.

| Dependencies | Runtime: 0 known vulnerabilities. Dev-only Tailwind CLI watcher deps (`braces`/`micromatch`) still flagged | Re-check `npm audit` on each release |

| Outbound integrations | Webhooks, email notifications, automations and heartbeat HTTP checks go only to admin-configured URLs; the Software page fetches a USD/INR rate from open.er-api.com (sends no company data) | Review configured URLs; set `USD_INR_RATE` to avoid the rate fetch |

| In-process state | Rate limits use the DB, but dashboard cache and the joinee single-flight guard are per process | With several instances, run `joinees:recommend` from one cron job |

## 3. Required Linux deployment steps

1. Install Node.js 20+ LTS and PostgreSQL 14+ (16/18 tested). Create the role and database as an admin:
   `CREATE ROLE <app_user> LOGIN PASSWORD '<strong>'; CREATE DATABASE <db> OWNER <app_user>;`
2. Copy the project (without `node_modules`, `storage/backups`, `.env`), then run `npm ci` (dev deps are needed for `npm run build:css`), then `npm run build:css`, then `npm prune --omit=dev`.
3. Create `.env` on the server (never commit it): `APP_ENV=production`, `APP_URL=https://<host>`, `APP_PORT`, a 32+ byte random `SESSION_SECRET`, and `DB_*`.
4. `node bin/hams-cli.js migrate` (creates tables, the `pg_trgm` extension and indexes). Run `seed` only on a new database.
   On a large live database, create the indexes in `database/performance_indexes.sql` with `CONCURRENTLY` in a maintenance window first.
5. Load data: `pg_restore`/`psql` from a backup, or `node tools/import-asset-data.js <export.csv>` (this **replaces** existing inventory data).
6. Run as a dedicated non-root user under systemd (`Restart=always`, `NODE_ENV=production`, `WorkingDirectory`, `EnvironmentFile=.env`).
7. Put nginx (or a load balancer) in front: TLS termination, `proxy_set_header X-Forwarded-Proto $scheme`, `client_max_body_size 10m`. Expose only 443; keep the Node port and PostgreSQL bound to localhost or a private network.
8. Cron: `backup:run-schedules`, `logs:cleanup`, `archive:purge`, `tokens:prune`, and `joinees:recommend` (e.g. hourly).
9. Make `storage/` (logs, sessions, backups, temp) and `public/uploads/` writable by the app user only.

## 4. Required security changes before production

Done in code (verified on a test instance):

- [x] **Default admin password**: signing in with a known default (`password`, `changeme123`) sets `users.must_change_password`; the account can then only use Profile/logout until it sets a new, non-default password. `seed` now creates a random one-time admin password (printed once), with no hard-coded credential. Bulk CSV-imported users (shared initial password) are flagged too.
- [x] **Secure session cookie**: `secure` is on automatically when `APP_URL` is `https://` or `APP_ENV=production` (`trust proxy` already set).
- [x] **No hard-coded secrets**: removed the `'it-hams-secret'` session fallback and the `'hams'` DB password fallback. With `APP_ENV=production` the server refuses to start unless `SESSION_SECRET` (32+ chars), a strong `DB_PASS` (12+ chars, not a default) and an `https://` `APP_URL` are set.
- [x] **Procurement uploads protected**: `/uploads/procurement/*` (invoices, POs) needs sign-in + `assets.view`; responses are `Cache-Control: private, no-store`; non-PDF/image files download instead of rendering. Avatars and branding logo stay public (the logo is shown on the login page).
- [x] **Vulnerable packages**: `xlsx` replaced with `exceljs` (Software import keeps CSV and .xlsx; old .xls must be re-saved as .xlsx); `npm audit fix`; `uuid` pinned to a patched version via `overrides`. `npm audit --omit=dev`: **0 vulnerabilities**.
- [x] **Agent enrollment key rotated** (no agents were enrolled; no API tokens exist).
- [x] **Backups/secrets not exposed**: `storage/` and `.env` are not web-served (verified 404); `.gitignore` covers `.env.*`, `storage/backups/**` and run logs.
